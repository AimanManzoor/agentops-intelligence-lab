# Local workflow run tracing

## Purpose

A final answer does not show which nodes executed, which work was skipped, or
where an unexpected exception occurred. The traced runner writes one local JSON
record for each invocation of the synchronous AgentOps graph. No external service,
API key, new dependency, or trained-model change is introduced by tracing.

## Run locally

From the repository root, activate the project environment. The real-model examples
require the existing local model artifact and database, just like the untraced graph.

```bash
python -m src.observability.run_workflow --example both
```

Use `--example high` or `--example low` to run one example, and `--trace-dir PATH`
to choose the trace directory. The default is the repository's ignored `runs/`
directory. The CLI prints a summary and the saved path for each example.

The Python interface returns the original workflow result and the trace path:

```python
from src.observability.run_workflow import run_with_trace

result, trace_path = run_with_trace({
    "pipeline_name": "payment_etl",
    "input_features": {
        "expected_workload": 9000,
        "cpu_usage_pct": 92.0,
        "memory_usage_pct": 88.0,
        "recent_failure_rate": 0.20,
    },
})
```

`build_graph()` still returns the untraced graph. `build_graph(trace=RunTrace(...))`
is the instrumentation hook used by the runner. Create a new trace for each
invocation; the runner does this automatically.

## Trace contract

| Field | Meaning |
|---|---|
| `schema_version` | Currently `1` |
| `run_id` | Unique UUID generated by the local runner |
| `pipeline_name` | Pipeline supplied to the runner, or null for a non-string name |
| `started_at_utc`, `finished_at_utc` | UTC wall-clock timestamps |
| `duration_ms` | Elapsed time including graph construction and execution |
| `execution_status` | `completed` or `failed` |
| `route_taken` | Final graph route, or null if execution failed |
| `investigation_status` | Final evidence status, or null if execution failed |
| `tool_errors` | Final structured tool/error-type pairs for completed execution |
| `error_type`, `failed_node` | Unhandled error type and failed node when identifiable |
| `events` | Completed/failed node invocations in execution order |

Each event contains the node name, UTC start time, elapsed milliseconds and status.
`completed` means the node callable returned; `degraded` means it returned a handled
tool error; `failed` means it raised an ordinary exception. Events may also contain
the returned investigation status and structured tool errors. A framework error
outside an instrumented node can produce a failed run with a null `failed_node`.

The low-risk path records validation, prediction and normal processing. The healthy
high-risk path additionally records SQL investigation and incident retrieval before
risk review. An unavailable SQL source produces a degraded investigation event,
skips retrieval, and still reaches risk review.

Completed execution is separate from evidence completeness. A run may have
`execution_status="completed"` and `investigation_status="partial"` or `unavailable`.
Neither completion nor a trace establishes prediction accuracy or causal truth.

## Timing and data boundaries

Durations use Python's monotonic `perf_counter`; UTC timestamps are for chronology.
Node duration measures the synchronous callable, not an entire LangGraph scheduling
step. Run duration includes graph construction and framework overhead and ends
before JSON writing. Directory creation occurs before the run timer starts.
Node durations therefore need not add up to the total duration.

The JSON record excludes feature values, prediction payloads, SQL rows, incident
labels, final messages, raw exception messages and stack traces. The CLI prints a
file path, but the JSON record contains no database/model path or trace-directory
path. This is a small defined logging contract, not a general-purpose redaction
system for arbitrary future fields.

Each run gets a different file name, opened exclusively. The runner writes after
completion or an ordinary exception and re-raises the original workflow exception.
If saving also raises an `OSError`, it adds the save-error type as an exception note
instead of replacing the workflow error. If an otherwise successful run cannot save
its trace, the save error propagates. A trace directory that cannot be created stops
the runner before prediction.

## Verification and research use

```bash
python -m unittest discover -s tests -v
```

The full suite contains 25 tests: 15 prior SQL/retrieval/reliability tests and 10
tracing tests. The tracing tests cover high/low-risk paths, node order and timings,
unavailable and partial evidence, unhandled model and validation errors, unchanged
workflow results, independent run files, trace-write failure behavior, an invalid
trace directory, and both CLI examples. They use temporary SQLite data, the real
graph and controlled prediction outputs, without a trained model artifact or APIs.

Research use: compare expected and observed node paths under controlled conditions,
locate failed stages, check whether low-risk requests avoid investigation, and
record timing for repeated experiments. Performance claims require controlled
hardware, warm-up, repeated runs, and reported variability. These tests do not
establish a latency improvement or production reliability percentage.

Limitations: synchronous local workflow only; no distributed traces, OpenTelemetry,
cross-process aggregation, dashboards, automatic retries, or persistence during a
node execution. Hard process termination can leave no trace or an incomplete file.
There is no trace-retention policy. Each node is currently deterministic orchestration
around tools, not autonomous LLM reasoning.
