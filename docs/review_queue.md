# Capacity-limited review queue

## Purpose
The previous threshold experiment exceeded its 20% validation alert limit on later
records. This module instead enforces a maximum number of selected runs in one
supplied batch. It is a standalone offline tool, not wired into live routing.

## Contract
Input: a list of at most 10000 unique run IDs and caller-supplied failure
probabilities. A record must have exactly run_id and failure_probability;
outcome labels and extra fields are rejected. Scores must be finite in [0,1].
The utility does not authenticate a score or prove it was generated by the model.

Eligibility is score >= min_probability (default 0.26 for comparison with the
existing workflow). Rank by descending supplied score, then ascending run ID
lexicographically for ties. Select at most budget records (integer 0-1000).
Validate every input even with zero budget. Do not mutate source records.

The CLI accepts at most 1 MB of JSON, rejects duplicate keys and performs no
network calls, model loading, SQL execution, remediation or review-state writes.
Only selected IDs/scores and aggregate counts are printed; human review is required.

## Run
Handcrafted demonstration, not trained predictions:

    python -m src.tools.review_queue --demo --budget 2

Expected selected order: run-B, run-C. Three records meet the threshold, two are
selected, one eligible record is deferred and one is below threshold.

For your own locally prepared score batch:

    python -m src.tools.review_queue --input scores.json --budget 10 --min-probability 0.26

JSON example:

    [{"run_id":"example-run","failure_probability":0.8}]

Only use trusted synthetic/approved data. The caller must extract the two accepted
fields from prediction outputs. Ranking uses the supplied score precision:
rounded scores can create extra ties. No unrounded score is inferred.

## Scope and research limits
This is a capacity ceiling per supplied batch, not a daily, concurrent, streaming
or persistent queue limit. Repeated invocations can reselect the same runs.
It can leave capacity unused when too few records meet the threshold. Deferred
or below-threshold runs are not determined safe, nor are selected runs proven failures.

Ranking a complete batch assumes all its scores are available at selection time.
Do not describe this as a real-time policy without an arrival-time protocol.
This milestone does not improve the model, estimate fraud risk, or demonstrate
better precision/recall, cost savings or workload outcomes. The existing graph,
prediction artifact and threshold remain unchanged.

Eight new tests verify the selection contract and CLI failure behavior. Combined
with the prior suite: 61 Python tests. Existing Actions discovery includes them.

Next research experiment: freeze an investigation budget and score floor, then
compare ranking against deterministic/random baselines on independent synthetic
batches. Measure failures caught, precision at budget, deferred failures and
review workload. Keep outcome labels outside the selector and join only afterward.
